# Release 2.1.50 (2026-11-24)

## CI

- **record why the package workflows keep a run-level concurrency group (#1010)**
  Both package-cleanup.yml and package-cache-warm.yml keep their workflow-level concurrency group, now with a comment beside it saying why and naming the trade-off with failure reporting. The group cannot move to the deleting or warming job: on a matrix job a job-level group applies to each leg, so one group name would cancel all but two legs of every run, and a group per package would let two runs put their legs on ghcr.io together, past the max-parallel cap of #652 (and, for the cleanup, would guard the #911 overlap only package by package). The cost is that a pending run replaced by a newer one is cancelled before any job starts, its report job included, so that cancel is not reported; it had done nothing, and the newer run does the same whole matrix and reports. test_ops_reporting.py now asserts that no reporting job has a concurrency group of its own and that only these two workflows have a run-level one, never cancelling a run in flight, with the reason recorded beside it.
- **read the automation App secrets from the automation environment (#1023)**
  Each caller of an App-key vergil-actions workflow passes secrets: inherit, and each job that reads APP_CLIENT_ID, APP_PRIVATE_KEY or GHCR_CLEANUP_TOKEN itself declares environment: automation. A new test pins both sets. Ref vergil-project/vergil-containers#1014.

- **log in to GHCR as the App for the dev rebuild (#1035)**
  nightly-rebuild-dev passes app-registry-login: true and the two App keys by name to cd-docker-publish.yml. With the input true, each push job declares the automation environment, mints an App token with packages: write and logs in to GHCR with it alone; a missing key, a failed mint or an empty token fails the job, with no fallback to GITHUB_TOKEN.
