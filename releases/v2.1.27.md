
# Release 2.1.27 (2026-08-23)

## Bug fixes

- **pin golangci-lint to v2.12.2 on Go 1.25 (#569) (#570)**
golangci-lint v2.13.0 (2026-08-19) raised its go directive to 1.26.0, so
'go install ...@latest' fails on the Go 1.25 image, which builds with
GOTOOLCHAIN=local and therefore cannot pull a 1.26 toolchain to satisfy the
requirement:

  golangci-lint/v2@v2.13.1 requires go >= 1.26.0 (running go 1.25.14)

This broke 'Build and push candidate' for dev-go:1.25 and prod-go:1.25 from
the 2026-08-20 nightly onward. It was masked because every publish job was
already red for the unrelated CVE cascade triaged in #567; clearing that gate
left go:1.25 as the only failing job.

Applies the treatment this file already uses for go-test-coverage: select
v2.12.2 (the last release carrying 'go 1.25.0') on Go 1.25 via the existing
'go env GOVERSION' switch, and leave Go 1.26 on @latest so the tool keeps
floating per the repo's unpinned-by-default doctrine. The shell variable is
named GOLANGCI_LINT_VERSION so extract_pins.py normalizes it to the tool name
without a new _ALIASES entry.

Checked every other module in the same RUN block against its current latest;
x/vuln, go-licenses, gocyclo and x/tools all still declare <= go 1.25.0, so
golangci-lint is the only one needing action.

Verified by running the exact tools block in golang:1.25 and golang:1.26 with
GOTOOLCHAIN=local: 1.25.14 selects and installs 2.12.2, 1.26.7 keeps @latest
and installs 2.13.1. check_pins.py passes with the new pins.yml entry, and
hadolint is clean on the generated Dockerfile.

- **keep exactly one bump PR open instead of one per run (#573) (#576)**
bump-tools branched on ${GITHUB_RUN_ID} and called 'gh pr create'
unconditionally, with no check for an already-open bump PR. A missed review
week therefore opened another PR rather than refreshing the waiting one. Five
had stacked since 2026-07-20 (#445, #455, #466, #518, #566), all describing the
same work.

That is not only untidy. Every run recomputes the bump from scratch on top of
the base branch, so each PR is a full snapshot and the newest strictly
supersedes the rest — meaning the visible drift was one piece of work
photographed five times, while trivy sat a month behind 0.74.0, the release
that vendors the golang.org/x/mod fix for CVE-2026-56864/-56865. A stalled
bumper delays security fixes reaching the images.

The step now lists open PRs whose head starts with 'bot/bump-tools-'. If none
exist it creates one exactly as before. If any do, it adopts the OLDEST — so
its number, URL and review history survive — force-pushes the freshly resolved
tree onto that branch, refreshes the body, comments that it was refreshed, and
closes the others as superseded. Because each run is a full snapshot, the
force-push is the semantically correct update rather than a rewrite of anyone's
work, and it clears any merge conflict the stale snapshot had accumulated.

The human merge gate is unchanged: #435 chose it deliberately and nothing here
auto-merges.

Verified by extracting this step's 'run' body straight from the YAML (no
hand-copied drift) and running it against a stubbed gh and a throwaway git
remote across all three paths: zero open PRs creates a new branch; one open PR
is force-updated in place with no new PR; three open PRs adopt the oldest by
number regardless of listing order and close the other two with
--delete-branch.

- **give the exposure report an auto-managed drift signal and actually run it (#574) (#577)**
The exposure report is documented as the observability view for a daily
morning-review ritual, but nothing invoked it and it had no signal for the one
thing that went wrong: five bump PRs stacking while trivy sat a month behind
0.74.0, the release carrying the golang.org/x/mod CVE fix.

Adds auto_managed_behind() as a SEPARATE signal rather than widening
due_for_reevaluation. That list means 'a break-hold whose inducing_release is no
longer leading edge, so the reason for the hold must be reconsidered' — a
question that does not apply to auto-managed tools, which carry no
inducing_release and are supposed to move. test_auto_managed_not_flagged_for_
reevaluation asserts that invariant deliberately; conflating the two would have
broken it. Both signals are now rendered, and the auto-managed section shows
pinned vs upstream instead of only a descriptive constraint.

Switches the upstream lookup from api.github.com to the same unmetered
/releases/latest redirect resolve_latest.py uses. #435 rejected the API there
for its 60/hr unauthenticated limit; that mattered less while this ran by hand
and matters now that it runs on a schedule. It stays best-effort — the bumper
must fail loud because it rewrites pins, but a read-only report must not fail a
build over one bad lookup, so ResolutionError is downgraded to a warning.

Adds --no-probe to skip the per-image Docker harvest, which otherwise emits
hundreds of ::warning:: lines and harvests nothing anywhere without a Docker
socket, including the prod-base container these jobs run in. Opting out
explicitly beats a silent partial result.

Wires both into workflows that run: a nightly non-gating ops job publishing the
report to the step summary, and the pins test suite into the existing CI pins
job.

That last one matters more than it looks. The suite was never run by any
workflow, so it rotted unnoticed: #569 legitimately re-pinned golangci-lint for
Go 1.25 and left test_pins.py asserting golangci-lint is unpinnable, red on
develop with nothing to report it. Corrected here — being freed by #418 does not
make a tool permanently unpinnable when upstream later forces a hold — and
replaced with a positive assertion that the pin and its pins.yml justification
agree.


## Chores

- **suppress x/mod sumdb pair + node-tar DoS blocking every nightly publish (#567) (#568)**
All 38 nightly publish jobs have failed the Trivy HIGH/CRITICAL gate since
2026-08-20. Three CVEs are responsible, all in vendored dependencies of
upstream prebuilt binaries — nothing this repo builds.

CVE-2026-56864 / CVE-2026-56865 (golang.org/x/mod < 0.40.0, sumdb) are the
pair #559 deliberately deferred while no carrier reported a vulnerable
x/mod. Trivy's DB has now ingested them and they gate every image, which is
the condition #559 recorded for adding them. The vulnerable code is the Go
module checksum-database client; the carriers (gh, scorecard, tofu, and the
go-install linters) vendor x/mod only to parse modfile/semver/module paths.
Corroboration from the scans: /usr/local/go/bin/go, the one real module
client in these images, is not flagged — the toolchain already ships the
patched x/mod. trivy is deliberately excluded from the suppression: 0.74.0
vendors x/mod v0.40.0, so that carrier is fixed by the bump in #566.

CVE-2026-73566 (node-tar 7.5.19, uncontrolled recursion in filesFilter)
requires a non-empty member-selection list, which npm does not pass when
extracting registry tarballs, and npm is build-time-only tooling here. It
is not fixable by bumping: the image already installs npm@latest, and npm
12.0.2 declares tar ^7.5.19 but bundles 7.5.19 lockfile-pinned. Verified by
direct inspection that exactly one vendored tar exists in the image.

Verified end to end against the published prod-base image using its own
trivy: 50 HIGH/CRITICAL findings with the ignorefile disabled, 0 with this
change (exit 0), with all three CVEs reported on exactly the carriers
documented in the new comment blocks.

- **float go-test-coverage on Go 1.26; keep only the Go 1.25 hold (#571) (#572)**
The go-test-coverage pin existed solely because v2.18.4+ requires Go >= 1.26
and so cannot install on the Go 1.25 image. The 'else' branch was separately
hand-set to v2.18.8 — whatever was current when the pin was written — and had
since gone stale: upstream is at v2.19.0, which declares 'go 1.26' and installs
cleanly on the Go 1.26 image.

Holding a version nobody constrained is exactly the hand-maintained drift epic
vergil-project/.github#155 set out to remove ('default is unpinned'), so the
Go 1.26 branch floats back to @latest. The Go 1.25 branch keeps v2.18.3, which
is a real, justified pin, and pins.yml keeps its entry with inducing_release
2.18.4 unchanged — that is still the release that forced the hold. The
constraint is restated as '==2.18.3 on Go 1.25, else latest (unpinned)'.

This mirrors the shape applied to golangci-lint in #569: constrain only the
branch that is actually constrained. extract_pins now reports a single
go-test-coverage 2.18.3 instead of a 2.18.3/2.18.8 pair, and CATALOG.md
regenerates to match.

Verified by running the generated RUN block in golang:1.25 and golang:1.26 with
GOTOOLCHAIN=local: 1.25.14 installs go-test-coverage v2.18.3, 1.26.7 installs
v2.19.0. check_pins.py, generate_catalog.py --check, hadolint on the generated
Dockerfile, and vrg-validate all pass.
