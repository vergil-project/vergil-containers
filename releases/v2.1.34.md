
# Release 2.1.34 (2026-11-07)

## Bug fixes

- **restore the image Trivy gate for CVE-2026-78661 (#756)**
* fix(security): bump trivy to 0.76.2 and opentofu to 1.13.9

Run the upstream-refresh hook (docker/pins/upstream-refresh.sh), the same bump the open upstream-refresh PR #752 carries. trivy 0.76.2 is built with golang.org/x/net v0.62.0 and go-jose v4.1.6, which fixes CVE-2026-78661 in /usr/local/bin/trivy. opentofu 1.13.9 is the newest release but still requires x/net v0.57.0, so it does not clear the finding. Ref #755

* fix(security): document the CVE-2026-78661 x/net/html carriers in .trivyignore

Every image's Trivy gate fails on CVE-2026-78661 (golang.org/x/net/html, fixed in x/net 0.62.0). The newest releases of gh, nfpm, scorecard, tofu, osv-scanner and go-licenses all still require an older x/net, and none of them links the vulnerable HTML tree builder (Parse and the parser's addText / fosterParent), per the function names in each binary. Add a documented entry with the carriers, that reasoning and the removal condition, and update the tofu and trivy carrier notes for the 1.13.9 and 0.76.2 bumps (trivy 0.76.2 also clears CVE-2026-116587). Ref #755

- **retry transient network fetches in image builds and attestation (#759)**
* fix(images): retry every build-time curl and stop piping downloads

Every curl in the image fragments now carries --retry 5 --retry-all-errors --retry-delay 2 and writes to a file, never a pipe: curl only discards a failed partial transfer before retrying when it writes to a file. The uv installer is downloaded to a file instead of piped to sh, and is run up to 3 times because it fetches the uv release with no retry of its own; the last failure fails the RUN. docker/pins/test_fetch_retries.py enforces the rules on every fragment and template. Ref #743.

* fix(ci): retry a failed build-provenance attestation once before failing the publish

attest-build-provenance has no retry input, so each publish job now runs it as attempt 1 (continue-on-error), a bounded jittered back-off, attempt 2 (no continue-on-error, so its failure fails the job and promotion never runs) and a loud report, the shape package-cleanup.yml uses. docker/versions/test_attest_retry.py pins the structure and runs the back-off and report scripts. Ref #743.


## CI

- **keep the manifest cache warm with a mid-week restore (#758)**
The cleanup action keeps its manifest cache in the Actions cache, keyed
ghcr-manifest-v1-<owner>-<package>-<run id> and restored by prefix. GitHub
evicts an entry not accessed for 7 days, and the weekly scheduled run starts
hours late, so the gap can pass 7 days: the 2026-11-01 run started 7d2h after
the previous one, cold for every package, and fetched 37,500 manifests.

Add package-cache-warm.yml. Every Wednesday it restores each package's newest
entry with actions/cache/restore, using the action's exact cache path and key
prefix. A restore is an access, so the entry stays inside the window and costs
no ghcr.io requests. This is cheaper than a second weekly cleanup run, which
would refetch about 16,800 manifests a week (the warm 2026-10-18 run), because
a dry run drops the digests it would delete from the cache it saves, and would
add a second deletion pass once deletions are armed. No new key is saved on a
hit: the restored entry is unchanged, and the cleanup saves its own new key.

On a miss the leg warns and rebuilds the cache with a dry-run of the action
whose delete-tags selector matches no tag, so every fetched manifest is kept,
then restores again and fails loudly if the entry is still missing (the cache
scheme no longer matches the action version).

The package list is generated from docker/versions/manifest.yml like the
cleanup's. test_package_cache_warm.py pins the cache scheme, the shared action
version, the literal dry-run, read-only permissions and the mid-week schedule.
package-cleanup.yml gains only a comment pointing at the new workflow; its jobs
and PACKAGE_CLEANUP_DRY_RUN arming are unchanged.
