
# Release 2.1.33 (2026-10-28)

## Bug fixes

- **cap fan-out and retry the cleanup action once on ghcr.io 429s (#703)**
The 2026-09-27, 2026-10-11 and 2026-10-25 scheduled runs failed with 'Request failed with status code 429' from ghcr.io while the action loaded manifests on a cold manifest cache, with all 32 matrix legs started at once. The action's own per-request retry (3 tries, sub-second backoff, honours Retry-After) ran out within seconds. Cap each job at max-parallel 3, and retry the action once per leg after a bounded, jittered backoff; a second failure fails the leg with an explicit rate-limit error. Tests pin the structure and run the backoff and report scripts. Ref #652

- **fail the build when the NodeSource Node install falls back or mismatches (#704)**
Replace the piped setup_<major>.x script, which exits 0 even when its own apt update fails, with a shared common/nodesource-node.dockerfile fragment. The fragment configures the NodeSource keyring and source directly, pins NodeSource nodejs to 1000 and every other origin's nodejs to -1, runs apt-get update with APT::Update::Error-Mode=any, and after the install asserts that node is major NODE_MAJOR and that npm exists. Both NodeSource installs (common/node-markdownlint and ts-node) include it; generate.sh now expands nested includes, with a depth cap so a cycle is an error. Ref #657

- **run every quality / pins step in local vrg-validate (#705)**
validate-custom ran only the docker/versions steps of CI's pins job. It now also runs check_pins.py, generate_catalog.py --check, and the docker/pins pytest suite, with the same commands and working directories as CI, in CI's order. Fail-defer is kept: every check runs and any failure exits nonzero. Ref #662

- **file lifecycle-check issues under the containers ad-hoc epic (#707)**
Every issue publish.py opens is now linked as a native sub-issue under the repo's ad-hoc epic (Epic (ad hoc): <repo> in <owner>/.github), so the nightly epic sweep no longer moves it into the intake queue. The epic is looked up by title and labels before anything is created; if the link fails the new issue is closed again and the run fails. Refreshing an existing issue never touches its parent. The issues step in ops.yml now uses an App token scoped to this repo and .github with issues: write, because GITHUB_TOKEN cannot add a sub-issue in another repository. Ref #687

- **separate dev and prod Trivy image scans in code scanning (#710)**
Prefix the image Trivy SARIF category with the image prefix (trivy-image-<prefix>-...), for both the amd64 (shared action) and arm64 (direct upload) paths, matrix images and base. Nightly prod results are filed under refs/heads/develop alongside dev, so the shared category let one overwrite the other. Update the Trivy scanning architecture doc to match. Ref #697

- **distinguish a Trivy scan error from CRITICAL/HIGH findings in the publish gate (#722)**
The publish gate failed with 'Trivy found CRITICAL/HIGH vulnerabilities' whenever a scan step failed, so a scan that crashed before writing a report (dev-rust:1.92 in CD run 40349047526, dev-go:1.26 in the nightly rebuild) blocked a clean image as a security finding.

The arm64 scan moves into scripts/bin/trivy-image-scan, which retries a scan that writes no report with backoff and records passed, findings or error. The new scripts/bin/trivy-gate replaces the 'Fail if vulnerabilities found' step: per platform it reports a missing report or result=error as 'Trivy scan errored (no report produced)', findings as vulnerabilities, and never passes a platform without a report. The arm64 SARIF upload is skipped when there is no report. Both cd.yml and the ops.yml nightly rebuild call this workflow, so both are covered. The amd64 scan's retry comes from the shared trivy action (vergil-project/vergil-actions#1079). scripts/tests/trivy.test.sh covers both scripts and runs in validate-custom.

- **run the prod nightly from main's copy of the publish workflow (#733)**
nightly-rebuild-prod called develop's cd-docker-publish.yml against a main checkout, so steps needing files added on develop since the last release (scripts/bin/trivy-image-scan, trivy-gate) failed with exit 127. Calling the workflow @main keeps the workflow logic and the checked-out tree on the same ref. Ref #731.

- **ignore new undici and go-jose CVEs that have no reachable fix (#734)**
The 2026-10-28 nightly dev publish failed the Trivy gate on three new HIGH findings, none fixable by a bump or rebuild: CVE-2026-87018 and CVE-2026-109383 in undici 6.29.0 bundled in npm 12.2.1 (the newest npm), and CVE-2026-116587 in go-jose v4 inside scorecard 5.6.0, tofu 1.13.2 and trivy 0.76.1 (each the newest release). Add dated, reasoned entries with revisit conditions. Ref #732.

Ref vergil-project/vergil-containers#717.
