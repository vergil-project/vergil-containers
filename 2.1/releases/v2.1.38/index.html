    Release 2.1.38 (2026-11-11)¶

    Bug fixes¶

    • wrap semgrep to cap the stack hard limit, and scan at build time (#827)
    • fix(base): wrap semgrep to cap the stack hard limit, and scan at build time

    On Python 3.15 RLIM_INFINITY reads as 2**64 - 1, so semgrep's setrlimits_preexec_fn turns an unlimited stack hard limit into a finite ~5 EiB soft limit for semgrep-core, which segfaults (exit -11) on every scan. base's semgrep and pysemgrep entry points become sh wrappers that lower the hard limit to 2929688 KiB (hard / 3 = 1,000,000,000 bytes, as on Python 3.14) when it is unlimited or larger, warn if they cannot, and exec the tool environment's entry point. checks-invariants.sh now runs a real minimal scan through both entry points, so every image built on base reruns it, and resolves a wrapper's exec target in its core-Python check. Remove the wrappers once semgrep fixes this upstream (#826). Ref #825

    • docs(base): document base's semgrep stack-limit wrappers

    Features¶

    • pin the language toolchains by version and hash, refreshed daily (#816)
    • feat(pins): pin the language toolchains by version and hash, refreshed daily

    Add docker/pins/toolchains.yml and resolve_toolchains.py, one fetcher per upstream (python-build-standalone, go.dev, nodejs.org, the Rust channel manifest, rustup). check_pins.py requires exactly one pin per manifest series of python, go, rust and ts-node plus the core Node major, with both architectures' hashes where a download is verified. The manifest gains a required core: section. generate.py carries the pins into each matrix entry's build-args, CATALOG.md gains a toolchains table, and the upstream refresh resolves the pins and then regenerates the matrix and catalog. Part of vergil-project/.github#649 (Task 6).

    • docs(pins): document the language toolchain pins and their daily refresh

    • test(pins): check the live matrix against the live pins without naming a live version

    test_live_matrix_embeds_the_live_pins indexed go 1.27, so dropping that series would break an unrelated test (#654). It now checks every live family row's build args against the live pins.

    • build base on pkg-ubuntu 24.04 with vergil-python and a side-by-side Node (#818)
    • test(base): add base's build-time check scripts, the invariants and the defaults

    checks-invariants.sh holds what every image built on base keeps and checks-defaults.sh one check per base default, for a language image to rerun by name; checks.sh runs both for base. They read the core series from base's ENV. Run in today's prod-base (Debian 13), they fail on the OS release, the missing core Python, the uv tools not on it, the markdownlint wrapper, the vergil apt source and all three defaults. Ref vergil-project/vergil-containers#779.

    • feat(base): build base on pkg-ubuntu 24.04 with vergil-python and a side-by-side Node

    base is now FROM ${PARENT_IMAGE}, the manifest's new base parent pkg-ubuntu 24.04, and removes the package toolchain marker in its first layer. uv and nFPM come from the parent, so base drops uv's pip install and nfpm.dockerfile.

    Four new fragments, which only base includes, install the core runtimes side by side under /opt/vergil/: vergil-apt (the vergil apt repository, set up only after the signing key's primary fingerprint matches the pinned one), core-python (vergil-python, with /usr/local/bin/python3 linked to it), core-node (the pinned nodejs.org tarball, hash-checked, with markdownlint-cli and a wrapper that runs the core node by path) and core-tools (yamllint, ansible-lint, semgrep and mkdocs with mkdocs-material and mike, as uv tools on the core Python). Nothing is pip-installed and no node, npm, npx or pip is on PATH.

    generate.py emits base's build args from the manifest's core: section and the core Node pin (CORE_PYTHON, CORE_NODE_MAJOR, CORE_NODE_VERSION and both architectures' hashes), and the docs tables name an entry's manifest parent as its base. base ENV-persists the core series, copies the check scripts into the image and runs checks.sh as its last step.

    Ref vergil-project/vergil-containers#779.

    • chore(trivy): ignore the 9 HIGH CVE IDs in the core Node 22's bundled npm

    The core Node 22.23.4 that base now carries at /opt/vergil/node/22 bundles npm 10.9.9, whose vendored brace-expansion, picomatch, sigstore, ip-address and pacote carry 9 fixable HIGH CVE IDs (spike vergil-project/.github#982, item 9). The runtime's npm is never upgraded in place (spec §5.8) and no newer Node 22 exists, so each is a carrier-group entry with its reason and removal condition. The undici group's carrier note no longer counts dev-base, whose npm is the core Node's own. Ref vergil-project/vergil-containers#779.

    • fix(base): check core-node's build args in POSIX sh, for hadolint SC3053

    • build python images on base, with a pinned toolchain (#822)

    • test(python): add the python image's build-time checks

    checks.sh reruns base's invariants and its no-node default, then checks the family Python: python-build-standalone at /opt/python/, python3, python, python, pip and pip3 in /usr/local/bin linked into it, python3 --version is the series, uv with UV_PYTHON_PREFERENCE=only-system finds it and no uv-managed interpreter exists, and no pytest-xdist. Run in today's prod-python:3.15 (Debian 13), it fails on the OS release, the core runtimes and uv tools base adds, the vergil apt source, check_no_node, the missing /opt/python/3.15, the python3/pip links, uv's discovery and pytest-xdist. Ref vergil-project/vergil-containers#780.

    • feat(python): probe python-build-standalone for an installable python series

    The python lifecycle adapter called a series installable when Docker Hub had python:-slim. The image now unpacks a python-build-standalone build instead (spec §5.4), so the adapter asks Task 6's python-build-standalone fetcher: a series is installable when a recent release has an install-only build of it for both amd64 and arm64. resolve_toolchains gains pbs_series_builds, the search resolve_python already pinned from, so the adapter and the daily refresh agree on what can be pinned. A failed or malformed upstream raises SourceError, never reads as not installable. The runtime_published check of the vergil apt index is unchanged. Ref vergil-project/vergil-containers#780.

    • feat(python): build python images on base, with a pinned toolchain

    dev-python is now FROM ${PARENT_IMAGE}, with parent base latest in the manifest, so it is a tier-2 image. It includes no fragment: base brings the common tooling and its core runtimes. The image adds only the family Python: the python-build-standalone install-only build of the series from Task 6's pins (TOOLCHAIN_VERSION, PBS_RELEASE and both architectures' hashes), checked against the TARGETARCH hash and unpacked at /opt/python/. python3, python, python, pip and pip3 in /usr/local/bin link into it. Nothing is pip-installed: the old pip and setuptools upgrades, uv, yamllint, ansible-lint and pytest-xdist are gone. The last RUN is checks.sh. The generated matrix and docs tables are regenerated. The tests follow the parent: tier 2 is published, base's fragments reach python through base, and the nested-include test uses a synthetic tree. The docs describe the new image, and pytest-xdist is now a consumer's own dev dependency. Ref vergil-project/vergil-containers#780.

    • build go images on base, with a pinned toolchain (#823)
    • feat(go): build go images on base, with a pinned toolchain

    The go images are now built FROM base (manifest parent base:latest) and install the go.dev release pinned in docker/pins/toolchains.yml, checked against its SHA-256 for TARGETARCH, at /usr/local/go. They keep the golang images' environment (GOPATH=/go, GOTOOLCHAIN=local, PATH) and C toolchain, drop every fragment base already installs, and end with a checks.sh that reruns base's invariants and all three defaults and asserts go version, the Go environment, a cgo go run and the Go tools. The go lifecycle adapter now probes go.dev's release list through resolve_toolchains.go_releases instead of Docker Hub's golang tags. Part of epic vergil-project/.github#649 (Task 9).

    • test(go): keep the fragment-scope check over base and its children after the rebase onto python

    • build rust images on base, with a pinned toolchain (#830)

    • feat(rust): probe the Rust release channel for an installable series

    The rust lifecycle adapter now reads the series' channel manifest with the toolchain pins' own fetcher (resolve_toolchains.rust_release) instead of asking Docker Hub for rust:-slim. A 404 is not installable; any other failure is a SourceError. Part of epic vergil-project/.github#649, Task 10 (#782).

    • feat(rust): build rust images on base, with a pinned toolchain

    dev-rust becomes a child of base (manifest parent: base latest). It installs gcc, libc6-dev and pkg-config from noble as the C linker, then the pinned rustup-init (SHA-256 checked for TARGETARCH) installing the series' exact release on the minimal profile with clippy, rustfmt and llvm-tools, under the rust:-slim layout. Its last RUN is checks.sh: base's invariants, all three defaults, and the toolchain. Part of epic vergil-project/.github#649, Task 10 (#782).

    • build cpp-clang images on base, with a pinned toolchain (#831)

    • feat(cpp-clang): probe apt.llvm.org's noble suites in the Clang lifecycle adapter

    The cpp-clang image moves to base on Ubuntu 24.04, so a Clang major is installable when apt.llvm.org publishes llvm-toolchain-noble-. The trixie fixture becomes a copy of the noble index (2026-11-10). Ref vergil-project/vergil-containers#783

    • feat(cpp-clang): build cpp-clang images on base, with a pinned toolchain

    cpp-clang is now FROM base (manifest parent base:latest, publish tier 2). It drops every fragment base already carries and python-support, installs g++-14 so Clang selects GCC 14's libstdc++, takes Clang from apt.llvm.org's llvm-toolchain-noble-, and ends with a checks.sh that reruns base's invariants and all three defaults and asserts the Clang series, the libstdc++ selection, the clang-format/clang-tidy major and noble's cmake 3.28.3 and cppcheck 2.13.0. common/cpp-analysis.dockerfile's LLVM tools source moves from trixie to noble. The live-tree tests for the publish tiers and fragment scoping now derive the families built on base from the manifest. Ref vergil-project/vergil-containers#783

    • docs(cpp-clang): describe the shared C++ analysis fragment on base and noble

    Merge review R1: the fragment's header still said language images never build FROM one another and that cmake and cppcheck come from the Debian release. Ref vergil-project/vergil-containers#783

    • build cpp-gcc images on base, with a pinned toolchain (#832)

    • feat(cpp-gcc): probe noble's archive for a released gcc- in the GCC adapter

    The cpp-gcc image moves to Ubuntu 24.04, so the lifecycle adapter's installable check moves with it (spec §5.4): a major counts once noble publishes a released gcc- (..-) in its Release, Updates or Security pocket, read from Launchpad's published sources. A pre-release snapshot does not count. The Debian sources helper had no other user and goes with its fixture. Part of vergil-project/.github#649, Ref #785.

    • feat(cpp-gcc): build cpp-gcc images on base, with a pinned toolchain

    cpp-gcc is now FROM ${PARENT_IMAGE} with parent base in the manifest (tier 2), drops every fragment base already carries and python-support, and installs noble's own gcc-14/g++-14 (a released 14.2.0 from noble-updates; g++-14, not noble's unversioned g++ 13, for libstdc++ 14). Its toolchain comes from apt, so it has no hash pin. The shared cpp-analysis fragment's LLVM source moves to apt.llvm.org noble, and cmake and cppcheck are noble's own (3.28.3, 2.13.0). A new checks.sh, the template's last RUN, runs base's invariants and all three defaults, then the compiler, libstdc++, the LLVM tools and the cmake and cppcheck versions. The tier and fragment-scope tests learn that language images are built on base. Part of vergil-project/.github#649, Ref #785.

    • test(cpp-gcc): date the Launchpad fixture in the report-only adapters' docstring

    • build ts-node images on base, with a pinned toolchain (#833)

    • feat(ts-node): build ts-node images on base, with a pinned toolchain

    The ts-node family is now built FROM base (manifest parent base:latest). Its Node is the nodejs.org tarball pinned in docker/pins/toolchains.yml, checked against the TARGETARCH hash and unpacked at /opt/node/, with node, npm and npx linked into /usr/local/bin and npm's global prefix set to /usr. The template drops every fragment base already installs, python-support and the NodeSource Node, and no longer upgrades the bundled npm in place (spec 5.8). checks.sh reruns base's invariants and the python3 and pip defaults, then asserts the pinned node, npm root -g and that markdownlint is still base's wrapper on the core Node. The lifecycle adapter's probe moves from NodeSource's setup script to nodejs.org's release index, read with resolve_toolchains.node_releases. Epic vergil-project/.github#649, plan Task 13.

    • fix(security): triage the npm bundled in the ts-node family Nodes

    ts-node no longer upgrades its bundled npm in place (spec 5.8), so the pinned nodejs.org runtimes' npm is scanned as shipped. dev-ts-node:22 (npm 10.9.9) carries the 9 IDs of the core Node 22 group, and dev-ts-node:24 (npm 11.19.1) carries CVE-2026-102276 and CVE-2026-102278 from that group, the three undici IDs already listed, and CVE-2026-19534 (undici 6.28.0, WebSocket client only), which gets its own group. The carrier notes of the existing groups now name both images, with the runtime-use reasoning for ts-node, where consumers run npm. Trivy 0.76.2 scans of both arm64 images are clean with the file. Epic vergil-project/.github#649, plan Task 13.

    • fallback mirrors outside Canonical's domain for both architectures (#838) Give amd64 and arm64 an apt mirror list that ends with mirrors outside ubuntu.com (amd64: mirrors.edge.kernel.org, mirrors.dotsrc.org; arm64: mirrors.dotsrc.org, mirrors.mit.edu ubuntu-ports), rewrite ports.ubuntu.com to it on arm64, make apt-get update fail when no mirror serves an index (APT::Update::Error-Mode any), and add an APT_MIRROR build arg (VRG_APT_MIRROR in build.sh) that puts a nearer mirror first for local builds. The pkg-ubuntu build-time check now asserts the list and the error mode on both architectures. Ref vergil-project/vergil-containers#837
